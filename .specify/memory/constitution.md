## 核心原则

### I. 兼容性优先（NON-NEGOTIABLE）

本项目的存在理由是**书源生态**。裁决任何冲突时，优先级次序固定为：

**兼容性 > 性能 ≈ 视效与体验完整性**

- **"兼容性"特指书源兼容性**，而非与上游代码或结构的对应。本项目是**完整重构**，与上游无代码血缘：上游的包划分、类型命名、模块切分对本案没有约束力；上游受移动端限制所做的取舍（强制复制导入、后台服务形态、单窗口交互）在桌面没有沿用理由；上游没有而桌面该有的能力应当补上
- 需要向"上游怎么做的"看齐的**只有一处**：既有书源开箱即用、既有规则语义一致
- 兼容性的判定不靠主观判断，靠**可复现的一致性度量**（见原则 III）
- 遇到上游行为本身有缺陷时，以兼容性优先，除非该行为导致数据损坏或安全问题
- 理由：书源是这个项目不可替代的资产，性能与观感可以迭代改进，兼容性一旦丢失则用户直接流失。但"兼容"的对象是**书源生态**，不是上游代码库——把后者当作约束会让重构失去意义

### II. 干净室纪律（NON-NEGOTIABLE，合规红线）

本仓库是**全新独立仓库**，代码由零重写，许可证为 MIT/Apache-2.0。

- **禁止阅读或逐行移植**上游 Kotlin 实现（上游位于只读位置，仅作数据源）
- 上游代码只允许两种用途：**黑盒运行**以产生输入→输出对照数据；**行为存在性证据**（据此构造测试用例）
- 语义须依据**书源作者的原始规则**与**公开文档**独立推导
- 不得在注释、提交消息、文档中引用或摘录上游源码
- 合并前须过**干净室审查轴**（独立于五轴的额外检查）：确认无移植痕迹、无上游源码引用
- 理由：宽松许可成立的前提是真正的独立实现。一旦参看上游源码，衍生作品主张将站不住脚，整个许可选择随之失效

### III. 测试先行（NON-NEGOTIABLE）

- **没有失败的测试就不写生产代码**，无例外
- 循环：先写必然失败的测试并实际看到它失败（RED）→ 写刚好够通过的最少代码（GREEN）→ 绿灯后重构，不加新行为（REFACTOR）
- 修 bug 必须先写重现 bug 的失败测试（Prove-It）
- 跑测试用仓库自己的命令，不默认 `cargo test` 之外的臆测
- **一致性验证是本项目的特化形式**：差分测试（合成用例入仓库；真实书源对照数据不入仓库）是"兼容性优先"原则的落地手段，不是可选优化
- 理由：后写测试验证的是"这做了什么"，先写测试定义的是"这应该做什么"。在重写项目中，后者的价值加倍——它同时充当行为规格

### IV. 简单性与单向依赖

- 能用就行的最简单方案优先；易懂 > 聪明（KISS）
- 公共逻辑只存在一处，禁止复制粘贴编程（DRY）
- 不提前构建不需要的功能（YAGNI）；"无需考虑复用"是本项目的既定前提，不要为假想的复用抽象
- **crate 边界即架构，用编译期强制而非约定**：依赖方向单向；上层（界面/可选模块）只依赖核心接缝 trait，永不直接构造下层内部类型
- 引擎必须能在**无图形环境**下完整运行——这是架构约束而非部署选项
- 理由：在约十万行规模的重写中，错误的边界比错误的算法昂贵得多；编译器的强制比文档的约定可靠

### V. 安全无例外

- 边界处校验所有外部输入；**书源规则、响应内容、本地文件一律视为不可信输入**
- **脚本沙箱是安全边界**：JS 执行须设内存上限与执行中断（不得以线程终止兜底——Rust 中那是未定义行为）；脚本文件访问限制在数据目录内，越界须拒绝并报告
- 数据库查询全部参数化
- 禁止提交密钥；禁止在日志记录敏感数据（Cookie、认证头须脱敏）
- 抓取第三方站点须遵守书源声明的请求间隔，**不得绕过限速**
- 外部通信一律 HTTPS
- **禁止遥测与崩溃上报**：除用户明确触发的抓取外，不得产生任何网络外发
- 理由：本项目处理的是不可信的第三方脚本与非受控网络内容，沙箱是主要防线；隐私是产品承诺而非合规负担

### VI. 原子提交与主干开发

- `main` 始终可部署；功能分支短命（1-3 天）；feature flag 优于长分支
- 一次提交做一件逻辑完整的事；提交消息解释 why；格式化/重构与功能变更分开提交
- 实现切片 → 测试 → 验证 → 提交 → 下一切片；禁止堆积后的巨型提交
- 理由：小步快走让回滚、审查、二分定位都保持廉价

### VII. 不审查不合并

- 重要功能完成后、合并 main 前必须审查，不因"很简单"跳过
- 审查按五轴：正确性 → 可读性 → 架构 → 安全 → 性能
- 评论必标级别：[必须修复] 阻断合并；[建议修改] 需回应；[仅供参考] 不阻断
- bug fix 必须有回归测试；安全敏感变更必须过安全轴（原则 V）；**任何涉及行为对齐的变更必须过干净室轴（原则 II）**
- 理由：审查是最便宜的缺陷拦截点

### VIII. 可读性与显式契约

- 代码被读多于被写：自文档化命名，注释只写 why
- 注释规范遵循 AGENTS.md §注释，代码审查时检查其"必须加注释的位置"清单
- **凡为兼容上游语义而写的非常规代码，必须注明依据来源**（书源规则原文或公开文档），而非"照抄某实现"
- 显式类型签名；禁止生产路径上的 `unwrap()` / `expect()` / `panic!()`
- 模块接口先定义契约再实现；一切可观察行为都是承诺（Hyrum's Law），设计时即规划废弃
- 理由：在兼容性驱动的项目中，**为什么这样做**往往比**做了什么**更难还原，注释是唯一的载体

## 附加约束

### 体积纪律

`<20 MB` 是**目标基线，不是硬门槛**。

- 为体积牺牲兼容性或体验完整性是不允许的（原则 I 优先）
- 超出需记录原因，但不阻断交付
- S1 阶段的具体要求是"不引入与功能无关的体积膨胀"（未使用的静态依赖、重复的解析器实现等）
- 最终应用体积目标由 S3 规格承接
- 产出物体积须进入持续集成监控

### 平台承诺

- 三条平台线一致：Windows 10+ / macOS 12+ / 现代 Linux
- 不使用依赖系统运行时或需用户额外安装运行时的框架
- 不使用系统 WebView 作为界面基础

### 范围纪律

项目拆为 4 个子项目，各自独立规格：**S1 引擎内核 / S2 排版渲染 / S3 应用外壳 / S4 可选模块**。

- 每个子项目走完整的 spec → plan → tasks → implement 周期
- **不得在实现某一子项目时"顺手"实现另一子项目的内容**，即使代码上方便
- 规格中的"明确排除"段是范围护栏，实现时以它为界

## Governance

- 本宪法优先于其他所有项目惯例；冲突时以宪法为准
- **冲突消解顺序**：宪法 > 特性规格（spec.md）> 计划（plan.md）> 实现细节。规格若与宪法冲突，回改规格
- 修订程序：提出修正案 → 说明理由 → 更新版本与 LAST_AMENDED_DATE → 同步检查依赖文件（AGENTS.md、spec/plan/tasks 模板）
- 版本策略（语义化）：MAJOR = 删除或重定义原则；MINOR = 新增原则或实质性扩充；PATCH = 措辞澄清
- 每个实施计划（plan）必须包含宪法合规检查；违反宪法的做法无论多"临时"都不允许
- 原则 I、II、III 标记为 NON-NEGOTIABLE：修订它们需 MAJOR 版本升级并显式说明
