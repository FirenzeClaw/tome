## 1 · 中文排版规则的优先序与冲突消解

**背景**：MASTER.md 与世界排版惯例都要求"避头尾 + 禁则 + 标点挤压"，但三者会互相冲突（典型：一行末尾若塞入一个闭标点会超出容器，此时是挤压、悬挂、还是把前一个字挪到下一行）。001 没有定义任何排版规则集，MASTER.md §5.1 只给尺寸、不规定算法。

**候选**：

- **A**：硬序——① 标点挤压（在允许的压缩下限内）→ ② 行末标点悬挂（超出容器不超过半个字身时）→ ③ 整字回退（把前一个字符挪到下行）→ ④ 放弃禁则（记录例外）。顺序固定、可预测。
- **B**：软序——按"最小视觉代价"评分择优（每个候选排版方案算一个代价分，取最小）。更接近排版质量最优，但结果依赖代价函数，难以逐条写测试。
- **C**：不做挤压也不做悬挂，只做"整字回退"：遇到禁则就把相邻整字移到下一行。实现最简、最可预测，但会出现行末留白（参差）。

**倾向：A。** 理由：① 覆盖了 MASTER.md 的观感诉求（挤压让行末整齐）；② 每一步都有明确的触发条件，可逐条写成判定例/反例，符合 SC-001 的"每一条规则都要有判定例与反例"；③ B 的代价函数会成为调参黑洞，且"为什么这一行这样排"无法向用户解释；④ C 在中文正文上会出现大量右端参差，与 MASTER.md §5.1 默认 36em 版心的"纸书质感"目标相悖。**A 的第 ④ 步（放弃禁则）必须记录例外计数**，否则 SC-002 永远无法达标。

## 2 · 段落识别除换行符外是否还认"前导两个全角空格"

**背景**：spec §FR-001 已定为"段落只由换行符切分"。但中文网络小说与社区书源存在两种真实情况：① 书源返回的正文用 `\n` 分段但**首行带 2 个全角空格**（作者的缩进习惯残留）；② 某些源把整章正文塞成**一个巨长行**、靠前导全角空格标示新段。

**候选**：

- **A**：只认换行符（严格）。前导全角空格作为段内文本保留。
- **B**：换行符为主，**当且仅当**一章正文中的换行数量低于段落数阈值且检测到 ≥3 处"前导 2 个全角空格"时，启用"把前导全角空格视为段落边界"的启发式，并**记录诊断**供用户可见。
- **C**：始终把"前导 2 个全角空格"也视为段落边界。

**倾向：B。** 理由：① A 在情况 ② 下会把整章排成一个巨长段落，视觉上完全不可读，而用户看到的是"这个阅读器坏了"；② C 在正常的 `\n` 分段正文里会把段首的 2 个全角空格又切成一个空段，产生莫名其妙的空行；③ B 的触发条件是可测的、局部的，且"记录诊断"让用户能理解引擎为什么这么切——比静默选择任一种都更能解释。**代价**：B 引入一个启发式，与 FR-001 的"MUST NOT 依赖首行缩进"字面冲突，故必须由本裁决把 FR-001 的措辞改为"默认只由换行符确定；满足 <条件> 时启用……"。

## 3 · 字体内嵌策略 vs `<20 MB` 体积基线

**背景**：**这是本清单最需要用户裁决的一条。**
- MASTER.md §10：「字体族 → **打包内嵌字体**（衬线正文 + 无衬线 UI + 等宽），确保三平台一致；注意 <20MB 体积预算」
- 001 §Assumptions：「**不捆绑任何字体**；依赖系统字体并在缺失时给出明确指引」
- 001 宪法「附加约束·体积纪律」：`<20 MB` 是目标基线、不是硬门槛，"为体积牺牲兼容性或体验完整性是不允许的"，超出需记录原因
- 001 §Assumptions 另有一条：「渲染后端已在设计共识中定案、不再作为体积降级项；若 S0 或 S3 阶段发现体积显著超出目标，**由用户重新裁决**取舍方向」

参考量级（用于裁决时估量）：一个覆盖 GB2312 常用汉字的中文衬线字体子集约 3–5 MB；覆盖 CJK 基本区+扩展 A 的约 8–12 MB；UI 无衬线中文字体子集约 2–4 MB；等宽（Latin only）约 0.3–1 MB。三平台若各打包一套，总体积影响可达 15–30 MB 以上。

**候选**：

- **A**：**捆绑正文衬线体的一个中文子集**（覆盖 GB2312 常用字 + 常用标点，约 3–5 MB）＋ UI/等宽**不捆绑**、走系统字体。体积影响约 3–5 MB，可容纳在 20 MB 内（其余依赖已按 001 的 release 配置 LTO/strip 优化）。
- **B**：**完全不捆绑**，全部走系统字体 + 字体缺失时的回退链与明确指引（即回到 001 §Assumptions 的原始口径）。体积影响 0，但三平台观感不一致（macOS 用 Iowan Old Style/Songti，Windows 用 SunSim/宋体，Linux 可能落到无中文字形的默认衬线）。
- **C**：**按 MASTER.md §10 全套内嵌**（衬线 + 无衬线 + 等宽，三平台捆绑）。观感最一致，但体积很可能突破 20 MB 目标基线，需按宪法记录原因。
- **D**：**A + 允许用户放置自定义字体文件（不捆绑）**：默认捆绑 A 的子集，同时支持用户把字体放到数据目录并被优先使用。

**倾向：A（若用户接受约 3–5 MB 的体积代价），否则 B（并把观感不一致记录为已知限制）。**
理由：① MASTER.md §10 是用户拍板的设计稿，其中"确保三平台一致"是一条实质诉求，B 会让"纸书质感"这个设计身份在最常见的 Windows 平台上落空（宋体不是设计稿指定的字形风格）；② 宪法说体积是"目标基线非硬门槛"，且"为体积牺牲体验完整性是不允许的"——A 用 3–5 MB 换设计身份，符合宪法的裁决方向；③ C 的代价（UI 字体也内嵌）收益最小——UI 字体在三个平台上的系统差异远比正文衬线小，不值得为它付 2–4 MB；④ D 是 A 的超集、无额外成本，但"用户自定义字体"本身是一个新功能（需 UI 入口），建议列为后续增强而不是本规格范围。
**这一条我无法替用户决定**——它是宪法的"体积纪律"条款明确要求"由用户重新裁决"的那一类决策。

## 4 · 与 `preview.html` 原型的分歧以何为准

**背景**（已逐行核对原型代码，结论比初稿更精确）：
- **不冲突的部分**：原型 `.p { font-size:19px; line-height:1.85; text-align:justify }` —— 字号、行高与 MASTER §5.1 完全一致；`text-align:justify`（两端对齐）补充了 MASTER §5.1 未规定的一项（**但注意 FR-006 的标点挤压正是让 justify 在中文下不出问题的关键**：不做挤压的 justify 会把标点拉到字符之间产生"稀疏行"，见 OQ #1）。
- **原型还实现了一条 MASTER 未写死的算法**：`preview.html` 第 526–539 行把自动切换判据实现为 `usable >= 36em × fs × 2 + 64`（`PAGE_PAD_X=60` 为双页左右内边距），并在设置页的说明文案里逐字复述了 §5.2 的语义（"字号变化会实时重算阈值，切换时保留阅读位置"）——**这是对 em 制判据的第二次确认**（除 MASTER §5.2/§10 外）。
- **真正不一致的部分**（仅两处）：
  1. **段落缩进**：原型正文样例段落**无** `text-indent`（`.p` 里没有），而 MASTER §5.1 把"段首缩进 2em"列为默认并可切；
  2. **段落间距**：原型靠 `.measure { gap: 20px }`（Flex 布局间距）表现段间呼吸，而 MASTER §5.1 规定的是 `0.4em`（19px 字号下 ≈ 7.6px）——**20px 与 7.6px 差 2.6 倍**，若把原型当成规范会得到一个全站过大段距。
  3. **设置页无"段缩进模式"开关**：`preview.html` 的"阅读排版"卡片只有四项（正文字体/阅读字号/行高/分页模式，第 405–414 行），**没有** §5.1 那个"缩进与间距二选一"的开关。故"用户在哪儿切"这件事在样式稿里没有落点。

**候选**：

- **A**：**MASTER.md 为准**。对齐方式（原型有、MASTER 未规定）采信原型 = 两端对齐；段落缩进/间距采信 MASTER 的 2em/0.4em 与"二选一"。原型不作为验收依据（除对齐这一项）。
- **B**：**原型为准**：默认两端对齐 + 无缩进 + 段距 20px。
- **C**：MASTER 为准 + 段距**按 em 定义但从原型取观感上限**（即 0.4em 与 20px 之间由用户在设置里选，默认 0.4em）。

**倾向：A。** 理由：① MASTER.md 自称"唯一设计规范来源"（第 3 行），用户指令也明确"以 MASTER.md 为依据引用"；② 原型的 `gap: 20px` 是 Flex 布局的默认间距，写它的人未必在想"这是段距"，把它当规范是过度解读；③ 中文正文两端对齐是公认惯例且与"纸书质感"一致，采信原型这一项没有风险；④ C 引入一个不必要的"观感上限"概念。
**须补一处**：原型的"阅读排版"卡片缺"段缩进模式"开关，而 MASTER §5.1 说"用户可切"——**这个开关的界面落点在样式稿里不存在**，属 S3 的界面缺项（本规格只在 FR-015 要求该能力存在且可持久化，界面归属与 S3 的 plan 阶段确认）。

## 5 · 单页模式下是否也遵循"章起偶数页"

**背景**：MASTER.md §5.2 第 4 条："双页模式下章节衔接遵循书页语义：左页为偶数页、右页为奇数页，章节末尾自动留白补足至偶数页起新章（长按可关）"。只写了双页。

**候选**：

- **A**：**只在双页模式生效**。单页模式下章节紧接上一章末页之后，不留白。（字面解读）
- **B**：**两种模式都生效**，单页模式下每章也从偶数页开始（会产生单页的空白页）。
- **C**：只双页生效，但**单页模式下保留该设置项的开关**且默认关（用户在单页下打开也不生效，直到切到双页）。

**倾向：A。** 理由：① MASTER.md 只在双页语境里提这条，且理由是"书页语义"——纸张双面印刷才有奇偶页的物理意义，单页屏幕上留白只是纯粹浪费一屏；② "长按可关"暗示这是一个**偶尔需要**的行为（比如想固定某章从左侧开始），在单页下它没有可理解的用途。

## 6 · 竖排（直排）支持

**背景**：001 §明确排除列了"竖排排版（本轮无排版层，天然不含；**S2 的范围由 S2 规格自行确定**）"，即该决定被显式移交本规格。MASTER.md 全文未提竖排。任务书也把"竖排支持与否"列入待裁决。

**候选**：

- **A**：**本规格明确不做**，列为 Out of Scope，并在 004 或后续特性中作为独立能力提出。
- **B**：**本期做基础竖排**（行序右→左、字序上→下，标点旋转与竖排禁则），不含竖排下的双页与 Ruby（注音）。
- **C**：**本期只做"横排文本的竖向容器"**（即支持竖排的排版方向参数与几何，不做竖排专属的禁则与标点旋转），作为后续完整竖排的地基。

**倾向：A。** 理由：① 竖排的中文禁则与标点旋转是**另一套规则集**（横排的"避头尾"规则在竖排下字符集与方向都不同），做一半的竖排会给用户"能做却不正确"的坏体验，比不做更糟；② MASTER.md（用户拍板的设计稿）完全未涉及竖排，没有观感基线可以对齐，意味着它不在当前的设计意图内；③ 中文网络小说绝大多数是横排，竖排主要服务古籍与特定排版偏好，价值密度低于本层的其他缺项（字体内嵌、滚动模式）；④ C 会引出"竖排下的禁则用哪套"的伪选择，反而增加后续的兼容包袱。
**若用户选 B/C**，本规格的 FR-006（中文规则集）与 FR-011（版心计算）需要各增一条竖排分支，工作量预估增加 20–35%（标点旋转、竖排禁则、行序、双页归属）。

## 7 · 滚动阅读模式

**背景**：MASTER.md 的阅读器只有翻页形态（`preview.html` 的 `.rpage` / `.spread` 都是固定页），没有滚动形态。但桌面阅读器普遍提供连续滚动模式，而**滚动模式的架构含义很大**：它意味着没有"页"这个单位，分页预计算（FR-031）、书页语义（FR-013）、页码/剩余时间（MASTER §5.3 的进度展示）都需要第二种实现。

**候选**：

- **A**：**本规格明确不做**滚动模式，只做翻页；滚动模式如需则为独立特性。
- **B**：**做滚动模式**，但作为"超长单页"实现（整个章节是一页，视口滚动）；不享受书页语义，也不做分页预计算。
- **C**：做滚动模式 + 虚拟化（只排版视口附近的行），共享排版管线但绕过分页。

**倾向：A。** 理由：① 用户指令把"滚动模式 vs 翻页模式（样式稿只有翻页——要不要滚动模式？）"明确列为需要裁决的缺项，而 MASTER.md 的无滚动形态本身就是一种设计选择（书页语义、"第几页"、章末留白都是翻页专属的观感资产）；② B 的"超长单页"会让位置锚点的持久化语义变形（现在的位置是"第 N 页"，B 下要变成"滚动偏移"——而 001 的锚点是字符偏移，所以其实不冲突，但"进度百分比"的口径会变成两个），且 C 是真正的工程投入；③ 若现在不做，滚动模式将来可以是一个干净的新特性（它不修改任何现有 FR，只增加一个呈现形态）。
**若用户要 B**：本规格需增 FR"章节可作为单一超长页面呈现，视口内只绘制可见行"，且 SC-007（翻页 ≤16ms）需改写为"滚动时视口重绘 ≤16ms"。**若用户要 C**：还要处理"滚动不得触发抓取"（对齐 001 §FR-019b）。

## 8 · 阅读区工具栏的归属分界（§5.3 与 §7 的边界）

**背景**：MASTER.md §5.3 定义了阅读区工具栏的**行为**（隐形/热区/唤出/内容清单），§7 组件清单里没有 Toolbar 组件（只有 TopBar/Sidebar/…）。`preview.html` 的阅读器是一个**常显的 52px 顶栏**（`.rtop`），含返回/书名/进度/单双页分段/字号/月亮/更多——**没有实现 §5.3 的隐形行为**。

**候选**：

- **A**：**S2 拥有工具栏的呈现逻辑**（隐形/淡出/热区/唤出、内容清单与排布），S3 只是把它嵌进外壳并提供图标资源。理由：隐形行为与阅读区的鼠标活动强耦合，跨层会需要 S3 反向查询 S2 的状态。
- **B**：**S2 只提供"阅读区矩形与热区边界"，工具栏由 S3 实现**。理由：工具栏是"外壳 UI"，应由 egui 绘制，S2 只管正文绘制。
- **C**：**S2 实现工具栏的绘制（自绘），S3 提供动作回调**。理由：工具栏浮在阅读区之上，若由 egui 绘制则需要两套渲染层合成到同一画布，带来 z 序与输入路由的双重复杂度。

**倾向：A（本规格写"最小呈现能力"），并在 plan 阶段明确"S2 提供几何与状态机，绘制可由 S3 的 egui 完成"。**
理由：① 001 已定"egui 只做外壳 UI"——工具栏属于外壳 UI，让 S2 自绘会越过 001 的分层；② 但"何时淡出、热区在哪、鼠标移入是否唤出"这些**状态**必须与阅读区的输入处理处在同一层，否则 S3 要为每个鼠标移动事件回调 S2 再回来；③ 故正确的切法是：**S2 拥有"阅读区几何 + 沉浸态状态机 + 唤出/淡出事件"**，S3 拥有"把这些画出来"。
**这条需要用户在审查时确认**——它是 S2/S3 的接口分界，判错会让 S3 的实现凭空多一层跨层查询。

## 9 · 工具栏的具体数值（2.5s / 8px 热区）是否可验收

**背景**：MASTER.md §5.3 给了精确数值："鼠标静止 **2.5s**"、"只留 **8px** 顶部热区"。我核对了 `design-system/shots/` 的 8 张截图清单与 `preview.html` 的代码，**均未体现**这两个数值（原型是常显顶栏，没有任何热区或淡出逻辑）。故这两个数值只有 MASTER.md 正文一处出处，无法与"截图实际状态"交叉验证。

**候选**：

- **A**：**按 MASTER.md 正文采信**，2.5s 与 8px 作为可验收参数写进 FR/SC。
- **B**：采信但**放宽为范围**（如"静止 2–3 秒"、"热区 6–10px"），给实现留调优空间。

## 12 · 排版参数的默认值：段首缩进还是段间距？以及参数的作用域

**背景**：
- MASTER.md §5.1 把 `--reading-paragraph-indent: 2em` 与 `--reading-paragraph-gap: 0.4em` 并列，并注明"（缩进与间距二选一，用户可切）"——**没有说默认是哪个**；
- `preview.html` 的正文样例段落**既无缩进也无段距**（`.p` 无 text-indent、`.measure` 的 gap 是 Flex 布局间距），即原型无法指示默认；
- 另有一层：参数是**全局默认**还是**每本书各自覆盖**？001 的 `Book.read_config` 注释是"该书生效的排版配置（**覆盖全局默认**）"，即两者都存在——但"用户在阅读器里改字号"改的是哪一个？

**候选**：

- **A**：默认**段首缩进 2em**（符合中文纸书习惯）；字号/行高/主题等**全局生效**，段落排布模式与版心也全局；`Book.read_config` 只在用户显式"为这本书设置"时写入。
- **B**：默认**段间距 0.4em**（符合 `preview.html` 的观感：段间有呼吸）；其余同 A。
- **C**：默认缩进，但**所有排版参数都默认写到当前书上**（即一次调整只影响这本书）。
- **D**：默认缩进，参数全局生效，且**不提供**每本覆盖（把 `read_config` 留给后续）。

**倾向：A。** 理由：① 中文小说读者的强预期是"段首空两格"，而间距式排布在中文小说上会让每段变成一个"卡片"，与"纸书质感"目标相悖——除非用户明确选它；② `preview.html` 的无缩进更可能是演示稿的简化（正文在 `.measure` 的 gap 下逐段排列），不足以推翻中文阅读惯例；③ C 会让用户改一次字号只对一本书生效，是典型的"为什么我调了没用"体验陷阱；D 忽略了一个已存在的字段，不好；④ 001 的 `read_config` 语义（"覆盖全局默认"）已经蕴含了 A 的两级结构。

## 14 · 单双页切换的"手动覆盖"在参数变化后的失效阈值

**背景**：MASTER.md §5.2 第 3 条："用户可在工具栏手动覆盖为「自动 / 强制单页 / 强制双页」，手动选择在本次会话内优先于自动判定；**窗口尺寸变化超过一定幅度时自动模式重新接管（`[UNCERTAIN]` 实际阈值待真机验证）**"。设计稿自己标了 UNCERTAIN。

**候选**：

- **A**：**显式回落**——用户在工具栏手动选了"强制单页/强制双页"后**一直有效**，直到用户再改回"自动"；窗口尺寸变化不改变它。最简单、最可预测。
- **B**：**按幅度回落**——窗口宽度变化超过 25%（或超过 240px）时回到自动。设计稿字面倾向。
- **C**：**按语义回落**——只在"用户的手动选择在当前宽度下不再成立"时回落（如强制双页但宽度已容不下两栏）。
- **D**：**按会话+参数变化回落**——手动选择在"字号/行高变化"或"手动调整窗口"后失效，回到自动。

**倾向：C。** 理由：① A 的问题是用户在双页下强制单页、之后拉宽窗口会永远看不到双页（除非想起去点工具栏），而 MASTER.md 的意图明显是"手动是临时覆盖"；② B 的 25%/240px 是凭空数字，且用户**微调**窗口时（比如拖了个边）不应该把手动选择丢掉；③ C 只在"手动选择已经自相矛盾"时回落——这正是用户能理解的理由（"窗口放不下两页了，所以回到单页"），且它天然与 §5.2 的 em 制判据共用同一套计算；④ D 把"字号变化"也算作失效条件，但用户调字号时通常希望排布偏好不变（他刚刚才选的），把它算作失效反直觉。
**A 的良性一面**：可预测性最强、测试最简。如果用户更看重"我选了就是选了"，选 A 也合理——**这一条适合在 clarify 时让用户二选一**。

## 15 · 阅读记录的"阅读字数"如何计算

**背景**：001 §FR-026b 要求数据层记录"每本书的阅读时长与阅读字数"，`ReadRecord { read_seconds, read_chars }` 落库，且"数据层的记录行为 MUST 不依赖任何界面"。但**"读了多少字"的口径没定义**——是"翻过的页所含字符数"，还是"视口内停留超过阈值的字符数"，还是"页数 × 每页字符数"？

**候选**：

- **A**：**按翻页计**——每翻过一页，把该页的字符数累加进 `read_chars`。实现最简单、与任何"停留时长"统计都无关，且回翻时是否重复计数有一个明确规则（建议不重复）。
- **B**：**按停留计**——只有视口内停留超过 T 秒的页才计入（过滤快速翻页找章节）。更贴近"真的读了"，但引入一个隐式阈值与一套计时逻辑。
- **C**：**按字符去重**——记录本会话内已计入的字符区间并取并集，同一字不重复计。口径最准，但需要维护区间集合。

**倾向：A。** 理由：① 001 对阅读记录的要求是"可聚合为日/总量统计"，粒度上 A 已经够（用户关心的是"今天读了多少"）；② B 的阈值 T 是新魔法数字，且"什么算读"本就是个主观问题，用阈值伪装成客观度量反而更糟；③ C 的区间集合会让每次翻页都做一次集合运算与持久化，性价比低；④ A 的一个必要补充：**回翻同一页不重复计入**（用一个"已计入的最大页序号"作为水位），否则来回翻页会把字数刷上去。

## 16 · 高亮样式标识（`HighlightRule.style`）的词表

**背景**：001 定义了 `HighlightRule.style: String` 且注释明确"具体渲染由 S2 排版层解释"。但**词表没有定义**——我查了 001 spec/plan/data-model 与 `tome-source`/`tome-rule` 的全部测试，用到的值只有 `"red"` / `"blue"`（测试里的占位）。001 §FR-015 只说"产出的必须是与排版无关的字符区间"。故"`style` 字符串的取值集合"是一个**未定义的口子**：书源/用户配置写的任意字符串都会流到 S2。

**候选**：

- **A**：S2 定义**封闭词表**（如 `underline`/`background`/`bold`/`italic`/`color:<token>`），词表外一律回退默认效果 + 诊断。用户与书源只能从这个表里选。
- **B**：S2 定义**开放词表**（任何字符串都当作 CSS 风格的颜色名或 token 名解析），解析失败回退。
- **C**：**沿用生态既有约定**：既有书源/阅读器生态里高亮样式通常是一个颜色名或 `style` 短串，S2 直接按"颜色名 → 主题里的语义色"映射，未命中的颜色名走 CSS 命名色表，再未命中回退。

**倾向：C，并把 A 的"封闭词表"作为 C 的一个子集落地。**
理由：① 兼容性优先（宪法 I）——书源与用户配置里已经存在的 `style` 值（生态里多为颜色名）必须继续有效，B 的开放解析正是为此；② 但"任意字符串"不能全都交给 CSS 色表（它无法表达下划线与背景色两种渲染方式的区别）；③ 故建议：**先匹配 S2 定义的语义词表（可选性最高），未命中则按颜色名解析（背景色渲染），再未命中回退下划线 + 诊断**。这条**需要与 001 的规则作者约定确认**——若 001 侧后续要定义词表，应由 001 定义、S2 解释，而不是 S2 反向定义。

## 18 · 排版结果的缓存与失效（是否需要持久化分页结果）

**背景**：分页计算有成本（SC-009 要求重排 ≤150ms）。选项是**每次打开书时重算**，还是**把分页结果持久化**（次页打开直接命中）？001 的 `Book.read_config` 只存参数，不存结果。

**候选**：

- **A**：**不持久化**。每次打开章节时按需计算（并用 FR-031 的预计算在后台前瞻）。参数集作为缓存键的一部分只存在于内存。
- **B**：**持久化到 Pack 缓存或独立表**，键是（章节内容哈希 + 几何参数哈希），参数变化时失效。打开即可呈现，代价是多一份存储与失效逻辑。
- **C**：**持久化但只对"当前在读的少数章节"**（LRU，比如 3-5 章），随章节缓存一起清理。

**倾向：A（S2 首版），把 B/C 列为后续优化。**
理由：① 分页的输入（正文 + 几何参数）都是确定性的，重算的代价可测（SC-009 的 150ms 就是它的预算）；② 持久化引入"参数哈希碰撞/失效漏判"这类新故障面，而它带来的收益（打开书快一点）在 A 的预计算下大部分可被覆盖；③ 001 §FR-029/§FR-030 对**内容缓存**有严格的崩溃安全要求（落盘先于索引提交），若 S2 也写盘就必须继承同一套纪律，成本不小而收益有限；④ 注意 `Book.read_config` 的变化会立刻让 B/C 的全部缓存失效——这会让"每次调字号都重算全书"的收益归零。

## 19 · 正文行高的可调下限（MASTER 内部数值冲突）

**背景**：MASTER.md 两处对正文行高给了不同约束——§2.3「**正文行高 ≥ 1.75**，正文色永不低于 `--text-secondary`」（无障碍条款，与对比度表并列），§5.1「`--reading-line-height` | `1.85` | 行高（**可调 1.4–2.2**）」。用户把行高拖到 1.4 时，就违反了 §2.3。这是**输入材料内部的数值冲突**（同一文件的两节）。

**候选**：

- **A**：**可调下限抬到 1.75**（即范围 1.75–2.2）。§2.3 的无障碍判据优先，且它被放在"无障碍（WCAG AA）"标题下，语义上是硬约束。
- **B**：**保留 1.4–2.2**，把 §2.3 的 1.75 解释为"默认与推荐区间"而非硬下限（用户在明知挤的情况下自担）。
- **C**：**保留 1.4–2.2 但加提示**：把行高拖到 1.75 以下时给出非阻断提示（"低于舒适阅读行高"），不禁止。

**倾向：A。** 理由：① §2.3 是唯一一处把行高写成**不等式**（"≥"）的地方，用词是有意的；§5.1 的范围是参数表的默认值说明，两者冲突时不等式应优先；② 1.75 与 1.4 的观感差异很大（19px 字号下 33px vs 26px 行距），1.4 对长文阅读确实过挤，"可调"不等于"应当允许不舒适"；③ 宪法/MASTER §10 把无障碍定为"引擎级强制，非可选皮肤"，A 与该定性一致；④ C 的提示在阅读器里是干扰性的（用户正想专注调版式）。
**注**：这条与 OQ #14（手动覆盖失效阈值）、#12（参数默认值）同属"MASTER 内部需裁决的数值"，建议一并过。

## 20 · 「长按可关」在桌面端不可达

**背景**：MASTER.md §5.2 第 4 条：「章节末尾自动留白补足至偶数页起新章（**长按可关**）」。但 §7 的「交互状态（强制）」清单是 `default / hover / focus-visible / active / disabled`——**没有长按**；且这是桌面应用（鼠标/触控板/键盘），"长按"是触屏手势，在桌面上要么无对应操作，要么与拖拽/选择文字冲突。结果是：这个开关规范了但**用户事实上够不到**。

**候选**：

- **A**：改为**设置项**（放进 preview.html 已有的"阅读排版"卡片，与"分页模式"并列）+ 保留一个工具栏快捷入口。
- **B**：改为**双击**该空白页（或该页页脚）临时跳过。
- **C**：改为**阅读设置里名为"章节从新页开始"的开关**（措辞对齐用户认知），不做手势。

**倾向：C（形态）+ A（位置）。** 理由：① 桌面端没有"长按"的通用语义，任何把触屏手势机械映射到鼠标的做法都会与既有交互冲突（`active` 状态与长按时长无法区分）；② 这个开关是"偶尔想改"的设置项，不是高频操作，放设置卡片最合适，也让用户能发现它；③ 措辞上"书页语义/留白补足"对用户没有信息量，而"章节从新页开始"直接说明后果。
**归属**：开关的**能力**属本规格（FR-013 的书页语义必须可关），**界面落点**属 S3。故本规格只要求"该行为可配置且可持久化"，不规定它画在哪。**请用户确认 A/B/C 中的形态**。

## 21 · 键盘导航键位集与 `Esc` 的语义冲突

**背景**：MASTER.md §5.3 的工具栏唤出入口写「键盘 **`Esc` 之外的任意导航键** / `Ctrl+T`」，而 §7 把 `Esc` 分给 `Drawer`（"右侧滑入，含遮罩，**`Esc` 关闭**"）。两个语义会在"目录以 Drawer 形态打开、焦点在阅读区"时冲突。另外"Esc 之外的任意导航键"是**排除法定义**——它没有说哪些键算导航键，也没有说方向键/空格/PageUp/PageDown 各自做什么，这在实际使用中会直接导致"按了没反应"或"翻页方向反了"。

**候选**：

- **A**：**分层处理**：阅读区聚焦时 `Esc` 先"退出沉浸态/隐藏工具栏"；Drawer（目录/设置）打开时 `Esc` 关 Drawer（Drawer 在栈顶优先）。并**显式列出**键位表（左右方向键/空格/PageUp/PageDown 翻页，上下方向键滚动或行移，Home/End 到章首章尾，`Ctrl+T` 唤出工具栏，`Ctrl+K` 由 §7 的命令面板占用）。
- **B**：把 `Esc` 统一给"取消当前状态"（栈式取消），不区分阅读区与 Drawer。
- **C**：键位留给 S3 定义（本规格不写）。

**倾向：A。** 理由：① B 实际上就是 A 的行为（栈式取消），但 A 把它显式化为一张表，可测；② C 会把"翻页键"这件**属于 S2 的核心交互**推到 S3，而截图中没有键位信息可依赖（探索结果：`preview.html` 与 MASTER 只有 kbd：`Ctrl K`、`Esc`、`Ctrl+T`）；③ 方向键在竖排/横排下语义不同——但本规格已排除竖排（OQ #6），故左右=翻页、上下=章节间或行移，无歧义；④ 键位表是**可验收**的（每个键一条测试），符合本规格"无模糊形容词"的自审要求。
**建议**：键位表在 plan 阶段成文，并在 S3 的 plan 里与 `Drawer`/`Modal` 的 `Esc` 语义对齐。

## 22 · 原型与 MASTER 的判据阈值换算不一致（须核对）

**背景**：我发现**判据公式**两处一致、但**换算结果**两处不一致：
- MASTER.md §5.2 的换算表：`1180–1499px` 为双页 → 即**阈值 ≈1180px**（在 19px 字号、无侧栏的整窗宽度下）。
- `preview.html` 第 558 行：`threshold = 36em×19px × 2 + GUTTER + PAGE_PAD_X × 2 + 240` = `1368 + 64 + 120 + 240` = **1792px**。其中 `+240` 是侧栏宽度、`+120` 是双页左右内边距、`+64` 是中缝。

差异来源是"容器宽度"的**定义不同**：MASTER §5.2 的表格说的是"**容器**可用宽度"（即已扣掉侧栏与内边距之后的阅读区宽度），原型说的是"**窗口**宽度"（把侧栏 240 与内边距 120 也计入阈值）。两者在数学上可以自洽，但**表格里的区间标的是 px 且未注明是哪种宽度**——若实现者按"窗口宽度"理解 §5.2 的表格，会得到 1180px 这个明显偏小的值，从而在侧栏常驻时过早切双页（阅读区其实只够一栏）。

**候选**：

- **A**：**明确判据只作用于"阅读区可用宽度"**（已扣侧栏与内边距），MASTER §5.2 的表格加注"此为阅读区可用宽度，非窗口宽度"。规范表格保持原值（1180 ≈ 2×684 + 64 的近似）。
- **B**：判据改用**窗口宽度**，把侧栏与内边距计入，表格改为 1792px 一档。
- **C**：不改规范，只在实现里按 A 处理（表格的数值视为示意）。

**倾向：A。** 理由：① 判据的语义（"版心可用宽度能否容纳两个不小于 36em 的栏"）本来就只与**阅读区**有关，窗口宽度只是在无侧栏时的特例；② 把侧栏宽度计入判据会让"折叠侧栏"这个动作改变分页模式，而 §6 说侧栏折叠是布局自适应的一部分，与阅读排版无关——那是一个意外的耦合；③ 12 行表格里的数值本身是近似（1368+64=1432，与 1180 不符，说明写表格时按的是另一套内边距假设），故 C 的"视为示意"也有道理，但**必须让实现者知道**，否则会像原型那样算出一个不同的阈值。
**需用户/PM 确认**：表格里的 1180/1500 两档到底是"阅读区宽度"还是"窗口宽度"。这是**会影响用户可见行为的数值歧义**（切双页的时机）。
