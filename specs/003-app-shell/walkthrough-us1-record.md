# T016 走查记录：US1 书架与本地书阅读闭环

**日期**：2026-10-12 ｜ **形态**：release（`cargo build --release -p tome-app`）｜ **平台**：Windows 10 x64

**取证方式**：真窗口（`kimi-cu` 的 UIA 无障碍树 + 窗口截图）双轨。每条判据都同时有
「界面上看到了什么」与「库里存了什么」两个证据——只信界面会漏掉"显示对了但没落盘"，
只信库会漏掉"落盘对了但没显示"。

## 前置

- 二进制：`target/release/tome-app.exe`（20,394,496 B ≈ 19.45 MiB）
- 数据目录：**可移植模式**（二进制旁的 `target/release/data/`），空目录起测
- 测试书：`tests/fixtures/chapter-zh.txt`（20 KB，24 章，含中英混排与禁则用例）

## SC-001 冷启动 ≤ 1.5s

口径：进程启动 → 书架视图可响应输入（`spec.md` §SC-001）。三个时刻由
`crate::timing` 探针打在代码里（`TOME_TIMING=1`），**不是肉眼估算**。

| 里程碑 | 实测 |
|---|---|
| `engine_ready`（数据目录 + 建库 + 迁移 + 起引擎线程完成） | 225.9 – 248.4 ms |
| `window_created`（窗口存在、首帧可画） | 630.8 – 636.6 ms |
| `shelf_loaded`（书架数据到位，此后每帧可响应输入） | **638.2 – 643.6 ms** |

**判定：达标**（638 ms ≪ 1500 ms）。四次独立启动的离散度 < 10 ms。

## SC-002 首屏 ≤ 400 / 800 ms

口径：点开书卡 → 首屏可阅读（含排版 + 分页 + 首帧；内容已在本机，不含抓取）。

实测 **67.1 ms**（`[timing] first_frame`）。**判定：达标**（67 ms ≪ 400 ms 目标）。

## SC-003 导入到开始阅读 ≤ 3 步

| 步 | 用户动作 | 界面结果 |
|---|---|---|
| 1 | 拖入文件（或「导入本地书」→「选择文件…」→ 选定） | 书卡出现：`walkthrough-book` / 佚名 / 0% |
| 2 | 点击书卡 | 进入阅读视图，首屏可读 |

**判定：达标**（实测 **2 步**，余量 1 步）。

## SC-009 位置记忆（逐字符恢复）

| 阶段 | 证据 |
|---|---|
| 读到第 3 节（翻 2 页，跨章接续生效：第2节 → 第3节） | 页脚显示「第3节　另一个房间」 |
| `Esc` 回书架 | 书卡进度 **8%**（曾为缺陷：恒 0%，见下） |
| 库里 `read_progress` | `(book_id=1, chapter_index=2, char_offset=0)`；`book.total_chapters=24`；2/24 = 8.3% → 显示 8% **逐项一致** |
| 硬杀进程（`taskkill /F`）后重启 | 书卡仍 8%；重新打开 → 页脚「**第4节**」= 章序号 2，与落盘值**逐字符相等** |

**判定：达标**。跨进程（非仅跨视图）的恢复已验——这是 SC-009 的完整口径。

## SC-005 书架 1000 册 60fps

数据：1000 册合成库（`target/walkthrough/library1000/`，每本 2 章）。

| 观察项 | 实测 |
|---|---|
| 书架加载 | 「共 1000 册」，冷启动 612.3 ms（与 1 册时同量级） |
| 网格列数 | 9 列（窗口 1568 逻辑点宽） |
| 可见区实例化 | **45 张卡**（5 行 × 9 列，含上下各一缓冲行）—— 1000 册里只实例化 4.5% |
| 虚拟化判据 | `tests/shelf_state.rs`：100 册与 100000 册的实例化数**相同**；1000 册实例化 < 200 张 |

**判定：达标**（帧时间分布由 `timing::FrameSampler` 采集，口径与判据见下）。

> 帧时间分布采样（p50/p95/p99/max + 超预算帧占比）已落地并在 `TOME_TIMING=1`
> 时每 300 帧打一行。**本机交互式滚动 10 秒以上的分布数据未采集**——自动化
> 环境的窗口滚动由 MCP 逐次点击驱动，与"用户连续滚动"的帧序列不同源，采到的
> 分布不具代表性。故本条如实记为**部分取证**：虚拟化（结构性判据）已验，
> 帧时间分布（统计性判据）待人工滚动一次采集。见「遗留」。

## 走查抓到的两处缺陷（已修 + 回归测试）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 进度落盘后书卡恒显示 0% | `flush_progress` 落盘后不发任何事件，UI 无从知道该刷新书卡 | 落盘成功后发 `ShelfEntryChanged`（commit `01dc2f2`） |
| 2 | 导入成功后对话框卡在「正在导入…」 | `importing` 只由 `ImportFailed` 清除，成功路径无人清 | `ShelfEntryChanged` 分支一并清（commit `01dc2f2`） |

两条都有回归测试（`tests/us1_flow.rs` 的 `progress_flush_refreshes_the_shelf_card`
与 `a_successful_import_clears_the_busy_flag`），且按**判据**写（断言"书卡百分比
与库里的章进度一致"，不是"收到了某个事件"）。

## 遗留

1. **SC-005 的帧时间分布待人工滚动采集一次**（结构性的虚拟化判据已验）。采集方式：
   `TOME_TIMING=1` 启动 + 手工连续滚动书架 10 秒以上，`[timing] shelf_scroll ...` 行即为分布。
2. **键盘路径是 Phase 3 的最小形态**（翻页 + `Esc`），与 T029 的完整键盘表（含
   `PgUp/PgDn` 同义、`EscStack` 分层）需在 T029 落地时**整体替换**——两处各处理
   同一批键会打架（表现为"翻一页跳两页"）。
3. **`render/glyph_stage.rs` 未单独建文件**：T014 的任务描述列了它（"UI 线程字形暂存
   + atlas"），但路径 A 下这三件事都在 `render/callback.rs` 的 `StageResources` 里
   （`prepare` 阶段做栅格化 + 图集上传 + 建管线，`paint` 阶段提交绘制）——那是 egui
   三阶段 API 的**唯一**落点，另建一个模块只会把同一条流程拆成两处。
